## 2. Why It Was Done

* **Tracing was not implemented — flagged, not faked.** Task 4 says to instrument tracing "matching whatever tracing backend the rest of GraphGPT uses." Before writing any OpenTelemetry wiring, I searched the sibling services in this monorepo (`auth-service`, `memory-service`) for any existing tracing setup — `opentelemetry`, `jaeger`, or similar — and found none; every match was incidental (a third-party library's own internal test/observability code, not application instrumentation). The premise of the task — that a backend exists elsewhere to match — doesn't hold. Wiring OpenTelemetry to an invented backend nothing else in the system uses would produce spans nobody collects and a dependency nothing else needs, which is worse than not adding it: it would look like real observability infrastructure while being effectively inert. This is recorded here rather than silently dropped so it's a visible, deliberate gap rather than a missed task.
* **`app/api/middleware.py` was a genuine pre-existing gap, not new Phase 10 scope creep:** it was scaffolded in Phase 0 per the LLD's directory tree ("CORS, Correlation/Request-ID, request logging, security headers") but never implemented or wired into `main.py` in any phase since — `core/exceptions.py`'s exception handler has been silently reading a `request.state.request_id` that never existed since Phase 3. Phase 10's own task 3 ("ensure every log line... carries request_id... where applicable") is exactly the task that exposes this gap, so fixing it here — rather than filing it as a separate future concern — is squarely in scope, not adjacent scope creep.
* **`request_id` propagation uses `structlog.contextvars`, not an explicit parameter threaded through every function:** `configure_logging()` (Phase 0) already put `structlog.contextvars.merge_contextvars` first in its processor chain — that was seemingly built in anticipation of exactly this middleware, since nothing else in the codebase used contextvars before now. Binding once, in one middleware, at the top of the request, is what makes "every log line, deep in a service or repository, automatically carries request_id" true without editing every `logger.info(...)` call site in the codebase to accept and pass through a new parameter.
* **`processing_status_count` is wired at a single point — `FileRepository.update_status`, not at every call site that transitions a file's status:** since docs/LLD.md §4.2 already established that this is the *only* method allowed to write `files.status` (enforced by code review and the Phase 4/6/7 regression tests), it's also the one correct place to observe every transition exactly once, regardless of which service (`upload_service`, `quarantine_service`, `retry_service`, `version_service`, `processing_status_consumer`) triggered it — instrumenting each caller individually would be five places to keep in sync instead of one, and would risk missing a transition path added in a future phase.
* **`processing_status_count`'s actual scraped series name is `processing_status_count_total`, not `processing_status_count`:** found by running the metric through `generate_latest()` directly rather than assuming the configured name matches the output — `prometheus_client` auto-appends `_total` to any `Counter` name that doesn't already end with it (the library's own enforcement of Prometheus's own counter-naming convention). docs/HLD.md §21 names the metric `processing_status_count` (no suffix); the code keeps that as the *configured* name to match the doc precisely, and the test/consumer-facing reality (the `_total` suffix) is documented at the metric's definition so nobody re-discovers this by a failing scrape assertion later.
* **The MinIO readiness check is offloaded via `asyncio.to_thread`:** `Minio.bucket_exists` is a synchronous, blocking SDK call (uses `urllib3` under the hood, not `httpx`/`aiohttp`) — calling it directly inside an `async def` readiness handler would block the entire event loop for its duration, stalling every other in-flight request on the same worker process while MinIO is slow or down, which is precisely the failure mode a readiness probe exists to detect gracefully rather than cause.
